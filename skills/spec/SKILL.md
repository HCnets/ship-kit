# 需求解析

把需求变成可执行的计划。输入：$ARGUMENTS

## 初始化

1. 解析输入：需求描述文本，或指向需求文档的路径
2. 解析项目名（可选，默认从需求中提取）
3. 创建 `brainstorm/<项目名>/`

## Step 1：需求理解（3 分钟）

读取需求内容，提取：

```
目标：[一句话说清楚要做什么]
用户：[谁会用这个东西]
核心功能：[列出所有提到的功能点]
约束条件：[技术限制、时间限制、平台限制]
非功能需求：[性能、安全、可访问性等]
```

如果需求不清晰，列出需要确认的问题，等用户回答后再继续。

## Step 2：功能拆分（5 分钟）

把需求拆成 5-10 个可验证的功能点：

```
# | 功能名 | 一句话 | 输入 | 输出 | 验收标准 | 工时估算
```

验收标准必须是可验证的：能点击、能显示、能通过命令检查。
工时估算基于：单人全职开发，熟悉技术栈。

## Step 3：技术方案（3 分钟）

根据需求类型推荐技术栈：

```
需求类型 → 推荐方案
─────────────────────
Web 前端 → Astro / Next.js / Vue
REST API → FastAPI / Express / Flask
CLI 工具 → Python click / Node commander
全栈应用 → Next.js / Astro + API routes
AI 应用 → Python + LLM API
数据处理 → Python pandas / Node
移动端 → React Native / Flutter
```

输出技术方案：
```
框架：[推荐框架] — 理由：[为什么选这个]
数据库：[如需要]
部署：[推荐部署方式]
关键依赖：[核心第三方库]
```

如果需求涉及多个方案可选，列出对比让用户选。

## Step 4：风险评估（2 分钟）

```
风险 | 影响 | 概率 | 缓解方案
```

常见风险：
- 技术可行性不确定 → 先做 spike 验证
- 第三方 API 依赖 → 准备 fallback
- 性能瓶颈 → 提前做 benchmark
- 需求可能变更 → 先做核心，留扩展点

## Step 5：开发计划

按依赖关系排序功能，输出开发顺序：

```
Phase 1（MVP）：功能 1, 2, 3 — 可独立运行
Phase 2（增强）：功能 4, 5 — 丰富体验
Phase 3（完善）：功能 6, 7 — 锦上添花
```

**等用户确认方案和开发顺序后再继续。**

## 输出

写入 `brainstorm/<项目名>/spec-report.md`。
输出：`下一步：/rapid-prototype <项目名>`

## 约束

- 整个过程不超过 15 分钟
- 功能点必须有验收标准，不能是模糊描述
- 工时估算要务实，宁可多估不少估
- 如果需求不清晰，必须问清楚再继续，不能猜
- 技术方案要有理由，不能只说"推荐"
